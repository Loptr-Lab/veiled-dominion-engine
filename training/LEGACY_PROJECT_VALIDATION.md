
# Legacy Project Validation — Cross-Track Module

## Purpose

This module teaches trainees that bringing an older project back to life is a validation exercise, not merely a coding exercise.

The trainee learns to distinguish:

- inherited material from newly created work;
- technical reuse from legal permission;
- prototype evidence from production acceptance;
- gameplay telemetry from claims about player intent;
- sandbox success from canonical status.

## Reference environment

**Paragon ReBorn / Return to the Void** is the current game-development sandbox used to explore this pattern.

Its role is to provide a controlled environment for:

- character rebuilding;
- game-grid play;
- technical art;
- gameplay systems;
- accessibility;
- telemetry and balancing;
- aim-assist experiments;
- documentation;
- provenance;
- production-readiness evidence.

The sandbox does not automatically transfer any third-party rights or make sandbox work canonical.

## Exercise LV1 — Provenance inventory

Choose one inherited asset, rule, reference, document, or other project element.

Record:

1. source;
2. provenance evidence;
3. current/historical license or permission evidence;
4. intended technical use;
5. intended public/demo use;
6. unresolved questions;
7. replacement path.

**Pass condition:** the trainee does not describe an asset as “cleared” merely because it is available to download or already appears in the old project.

## Exercise LV2 — Rebuild boundary

Take one inherited gameplay concept and rebuild the implementation independently.

Document:

- inherited concept/reference;
- new implementation;
- tests;
- observable differences;
- dependencies that remain;
- dependencies deliberately removed.

**Pass condition:** the trainee can explain what was rebuilt rather than implying that inherited material transferred ownership or permission.

## Exercise LV3 — Data experiment

Run a bounded aim-assist or balance experiment.

Capture observable gameplay telemetry such as:

- hit/miss;
- time-to-target;
- target selection;
- assist activation;
- correction magnitude;
- movement;
- ability use;
- completion/death;
- relevant accessibility settings.

Document what the telemetry can establish and what it cannot establish.

**Pass condition:** telemetry is not presented as proof of player intent, personality, diagnosis, or other unobserved attributes.

## Exercise LV4 — Playability card

Rebuild a character until it:

1. loads;
2. moves;
3. executes its core abilities;
4. participates in the game grid;
5. can be played by its designer;
6. passes the playability card;
7. has documented evidence and known limitations.

This is the character-builder graduation gate.

## Exercise LV5 — Production handoff

Prepare a handoff that separates:

- demonstrated skill;
- sandbox artifact;
- third-party dependencies;
- original project material;
- unresolved rights questions;
- receiving-project requirements.

**Pass condition:** the trainee does not treat graduation as automatic employment, canon, ownership transfer, or production acceptance.

## Writer integration

Technical writers should join the validation record at the trainee's current milestone.

The writer records:

- what was actually built;
- what was observed in play;
- what changed;
- what remains unresolved;
- what can safely be stated publicly;
- what needs counsel or receiving-project review.

## Validation principle

A discovered restriction is not a failed exercise.

If the trainee identifies a rights, provenance, accessibility, data, or dependency problem and correctly stops, documents it, proposes a replacement, and retests, that is successful validation behavior.
