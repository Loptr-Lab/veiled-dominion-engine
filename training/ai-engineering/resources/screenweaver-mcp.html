Purpose and placement

Primary use case: maintain continuity across our creative projects. Creator OS coordinates the work and tools around it; ScreenWeaver is an optional external production tool for screenplay and storyboard tasks. We use our own stories, pitch projects, characters, worlds, concepts, treatments and production materials as test cases—not generic demo content. The goal is to preserve creative intent, canon, decisions, versions, provenance, rights and next steps as a project moves between research, pitching, writing, storyboarding, production and collaboration.

ScreenWeaver belongs in the Creator OS creative-production tool directory under storytelling, screenwriting and storyboarding—not in the core platform runtime. It is a replaceable tool, not the system of record for a project identity or history.

Canonical server URL: https://app.screenweaver.ai/api/mcp

Legal, brand and entity-status routing

Project continuity includes rights and contracting context. Before using ScreenWeaver with any Loptr Lab story, pitch, script, character, recording, image, contributor material or confidential project, check the Ecosystem brands & business-status register, BRAND-001 and ENTERPRISE-001. These distinguish documented project names from trademark ownership/clearance, project-level rights from entity ownership, and proposed business structures from formed entities. The register is now published in the Loptr Lab portfolio Legal & Rights section. It records official entity/trademark registry verification and independent professional review as pending; publication is not a legal clearance. Do not infer a contracting party, rights holder, clearance or legal entity from the Creator OS ecosystem map.

What it can do

  • List accessible projects and inspect project outlines.
  • Read scenes, search screenplay text, and list characters, places and objects.
  • Import supported screenplay formats after reviewing a preview.
  • Edit screenplay elements and create or update storyboard shots.
  • Set a project's aspect ratio.

The MCP prepares and edits screenplay/storyboard structure. It does not generate storyboard images or finished video through the MCP endpoint; those production actions remain in the ScreenWeaver application. Capabilities can change, so consult the live tool descriptions before relying on a specific operation.

Connection and access

  1. Create the project in ScreenWeaver first.
  2. In a compatible MCP client, add a remote server named ScreenWeaver with the canonical URL above.
  3. Complete ScreenWeaver's OAuth 2.1 sign-in and consent flow.
  4. Choose only the ScreenWeaver projects needed for the task; do not grant all-project access by default.
  5. Start with read-only tasks such as listing projects, reading an outline, or searching a script.
  6. Before any write operation, identify the target project and requested changes. Review import previews and confirm destructive script changes when prompted.

No API key is required. ScreenWeaver states that MCP access is included with its Auteur and Studio plans. Check the current plan and consent screen before planning a workflow. The service states that MCP tool use itself does not spend credits, while some other in-app production features may have separate costs.

Access can be revoked in ScreenWeaver under Connected apps. Project permissions matter: viewers can use read operations; owners and editors can make changes.

Transport and authentication
Remote MCP over Streamable HTTP; OAuth 2.1. No API key or locally hosted server.
Data boundary
Project data is accessed by ScreenWeaver only after the user authorizes the connection and selects project scope. Use project-specific, minimum-necessary data; do not assume every Creator OS record belongs in ScreenWeaver.
Continuity and source of truth
Creator OS is the creative control plane. My PIXIE/Companion is the private identity, consent and project-persistence boundary for portable project records. ScreenWeaver is an external execution surface for selected screenplay/storyboard work. Preserve a canonical project record outside any single provider: stable project ID, premise/logline, canon and character/world facts, decisions and rationale, pitch/script versions, asset references, provenance and rights, collaborators/permissions, current status and next actions. Sync or export only with explicit user authorization. A provider connection must never silently overwrite canonical project history.
Credential handling
Do not commit OAuth tokens, session data, client secrets or user credentials to GitHub. Do not proxy or persist tokens in Creator OS unless a separately reviewed architecture explicitly requires it.
Action policy
Read first; use least privilege; require explicit user intent for edits; preview imports; confirm destructive script changes; report exactly what was changed. Record material edits as attributable project events with source, timestamp, version and approval; keep prior states recoverable.
Failure behavior
If OAuth, project access, or a tool call fails, stop and report the failure. Do not claim a script or storyboard was updated.
Fallback
Creators can continue with screenplay files such as Fountain or Final Draft and use ScreenWeaver directly; the Creator OS experience must not require this provider.

Continuity model: one project, multiple tools

The continuity layer must outlive any individual app connection. A project retains a stable identity and portable history even if a creator changes screenplay, storyboard, storage or production providers. ScreenWeaver receives only the selected working context and returns proposed or completed changes to reconcile against the canonical project record.

  • Identity: stable project ID, title, owners, collaborators and relationship to a larger pitch, story world or production.
  • Creative canon: approved premise, themes, characters, relationships, locations, world rules, chronology and intentional open questions.
  • Decision history: what changed, why, who approved it, which version it supersedes and what must remain unchanged.
  • Artifacts: pitch decks, treatments, scripts, scene breakdowns, storyboards, references and asset links, each with version and provenance.
  • Rights and consent: ownership/source, licenses, permissions, contributor attribution, likeness/voice/footage consent and reuse restrictions.
  • Workflow state: current phase, dependencies, outstanding questions, next actions and handoff notes.

Do not treat an MCP conversation, a ScreenWeaver project or a generated artifact as the complete project history. Reconcile changes deliberately; preserve originals and record conflicts rather than silently choosing a winner.

Our projects are the test suite

Use our own active stories and pitch projects as longitudinal test cases. Revisit the same project across sessions and tools to test whether its identity, canon, decisions, versions, rights and next steps remain intact—not merely whether one tool call succeeds.

  • Stories and story worlds: test continuity of characters, relationships, locations, chronology, world rules, approved facts and deliberate mysteries across outline, scene and storyboard revisions.
  • Pitch projects: test continuity from initial idea and audience/problem framing through logline, pitch narrative, deck, treatment, feedback, revision rationale and the current ask. Keep each pitch version and intended audience traceable.
  • NOT A TOY: use approved tour/music-video narratives, visual treatments and interlude concepts to test translation from creative intent into scene and shot planning without losing musical and visual direction.
  • PLAY IT FORWARD: use creator-approved stories and media projects to test source attribution, contributor permissions, narrative development and handoffs from source material to treatment/storyboard.
  • Deck Workshop: use game-world and card-project narratives to test characters, setting and presentation continuity while keeping rules, mechanics, card data and source-of-truth game assets distinct.

These are internal test candidates and proposed workflows, not claims that ScreenWeaver is already connected or that project data has been imported. Select only material we own or are authorized to use. Use synthetic or redacted samples for sensitive, embargoed or third-party material until permissions and data handling are reviewed.

Implementation status

  • Implemented in this documentation change: integration placement, endpoint reference, capabilities, OAuth/project-scope guidance, permission boundaries, action safeguards, continuity architecture, project test cases and limitations.
  • Not implemented here: an in-product Creator OS connector UI, automated OAuth handoff, live MCP tool invocation, token management, project sync, or server-side proxy.
  • Needed for a live connection: the user connects their own ScreenWeaver account and chooses project scope in the supported MCP client. Any future embedded Creator OS connector requires a separate technical design, security review and explicit authorization flow.
  • Validation still needed: test a real authorized account with read-only calls first; then test a disposable project for a reversible edit and confirm the ScreenWeaver History/undo behavior. No account connection or live project edit is claimed by this documentation.

Suggested validation sequence

  1. Baseline: choose one owned story or pitch project and capture its canonical brief, current version, approved facts, decisions, source references, rights and next actions in the continuity record.
  2. Read-only connection: authorize ScreenWeaver for one test project; list accessible projects and read its outline/scenes. Compare with the canonical record and note omissions or mismatches.
  3. Round-trip: on a disposable copy, make one small, reversible scene or storyboard change. Record the proposed change, user approval, resulting provider version and reconciliation into canonical project history.
  4. Cross-session recall: return in a separate session and retrieve the project premise, approved canon, latest pitch/script version, unresolved decisions and next steps. Verify against the canonical record, not model confidence alone.
  5. Portability: disconnect or make ScreenWeaver unavailable and confirm that project identity, history, assets and handoff remain usable without it.
  6. Conflict and recovery: test a stale version or conflicting edit on disposable data; ensure the conflict is flagged, both source states are preserved and resolution is deliberate.

Track continuity accuracy, provenance completeness, version integrity, permission enforcement, conflict detection, recovery and portability—not just MCP connectivity. Record client, date, account plan, project scope, tool availability, test input, expected and observed results, and errors without recording secrets. No live account connection or project edit is claimed by this documentation.
